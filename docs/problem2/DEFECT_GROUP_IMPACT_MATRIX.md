## Scope and evidence rules

All **DF-001–DF-018** are accounted for. The original workbook remains unchanged.
`WB:D` below means **Defect Log**; original TC links come exclusively from column
D. `DF-###/F##` are internal atomic findings, not replacement external records.
Groups concern shared requirements/behavior, **not a demonstrated common cause**.
All proposed classifications and wider impacts need human review.

Impact confidence has three meanings:

- **Confirmed by evidence:** the cited original record explicitly reports that
  observation/TC association. This confirms documentary provenance, **not** an
  independently reproduced violation, live root cause or current recurrence.
- **Plausible impact:** another TC/VAR exercises the same conditional requirement;
  no failure of that case is asserted.
- **Not established:** the applicable precondition, violation, cause, current state
  or wider effect lacks sufficient evidence. Each affected item states which.

The original reports are summaries, not complete synchronized transcripts/traces.
Positive observations and tester interpretations are retained separately. Seven
rows labeled “Missing or changed verbatim line” contain substantive process
concerns; none is dismissed or confirmed solely from that category (PB §6).

### Requirement-driven regression selection — reviewer procedure (proposed)

1. **Select the changed BR and exact condition**, rather than treating a whole `DG` as a single fix ticket. If a prompt change affects several BRs, evaluate each independently.
2. **Direct evidence:** include the original DF-linked TC fixture(s) that actually exercise the violated requirement. Preserve the original DF's historical status and do not call its observation a currently reproduced failure without fresh evidence.
3. **Additional impact:** include other TC/VARs linked through the same BR and relevant process family, but only when the changed requirement's prerequisite is present. Record these as `PLAUSIBLE_REGRESSION`, not newly confirmed defects.
4. **Negative controls:** select previously correct paths where the condition is absent (e.g. successful form visibility for a missing-form-role patch, recent education without navigation for a Portal route change). Protect these from overapplication of a fix.
5. **Distinguish outcomes:** assign separate behavior verdict and intended-target coverage verdict, with configuration, fixture, channel, and evidence identifiers. A pass on one branch never closes all other branches.
6. **Closure:** group-level verification is `NOT_ASSESSED` until required applicable coverage is defined; do not invent a single Open/Closed status for a DG containing mixed historical reports. A claimed shared root cause needs distinct component/trace evidence.

**Concrete example — DG-005 role/form access (not a claim of active defects):** the parent reports link DF-003/004/007/009/011 to TC-003/005/007/009. TC-006/008/027/029 are plausible additional coverage because they exercise form-access/submission behavior, **not** because Grab filed those DF IDs against them. For a `BR-012` retry fix, cover (i) form present/no retry, (ii) form absent + role known/unknown, (iii) separate retry acceptance/decline and one observed attempt, and (iv) consented transfer only if that branch is supported. TC-006's internal primary is the agreed declined retry under OD-001; formal benchmark attribution and dependent requirements remain pending. Do not require all eight TCs to run all branches: select cases where the precondition is actually true, and record exclusions.

`regression_selection` minimum record: `{changed_br, applicable_condition, source_df_finding, directly_reported_tc, plausible_tc_or_variant, positive_or_negative_control, reason, reviewer, result, evidence_ref}`. This is a documentation suggestion, not a runner schema modification.
